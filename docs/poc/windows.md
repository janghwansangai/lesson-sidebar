## 실행기가 예시 파일의 복사본을 열게 바뀐 뒤 (#8, 2026-11-21)
`node runner/run.js --only=P0,P1,F,P5,P6` (외부 모니터 연결): **통과 7 · 실패 0**. 파워포인트·엑셀·한글 모두 `poc/out/copies/`의 복사본(`F1_시각_샘플_….pptx` 등)으로 열기·앞으로·학생 화면 반쪽 배치·닫기가 맞았다.
- 오피스가 복사본을 "보호된 보기"로 열지 않았다 (예시 파일에 인터넷에서 받은 표시(Zone.Identifier)가 없음). 인터넷에서 받은 파일이면 보호된 보기로 열릴 수 있으니, 실제 앱에서 선생님이 받은 파일을 쓸 때는 따로 확인해야 한다.
- 창을 모두 닫은 뒤 복사본이 지워졌다 (`poc/out/copies/`가 비어 있음).
- 한글은 선생님 문서(`123.hwp`)가 열려 있는 상태에서도 복사본을 새 창으로 열었다.

## 알게 된 것

1. **앞으로 가져오기**: 명령줄 도우미가 보통 방법(`SetForegroundWindow`)으로 바로 창을 앞으로 가져왔다.
   - 아무도 키보드·마우스를 만지지 않을 때: 0.05초 (실행기 P2)
   - **선생님이 메모장에 글자를 치는 도중** (`raise-lock.js`, 맨 앞: 메모장): 0.06초, 보통 방법으로 성공. 윈도우의 포커스 가로채기 방지가 이 경우에도 막지 않았다. 이 PC의 포커스 잠금 시간(`ForegroundLockTimeout`)은 기본값 200초
   - 다른 PC·학교 PC에서는 막힐 수 있어서, 도우미는 막히면 ① 빈 마우스 입력을 보낸 뒤 다시 시도(PowerToys와 같은 방법) ② `AttachThreadInput` 순서로 자동으로 이어서 시도하고, 어느 방법이 통했는지 `detail.method`에 남긴다. 실제 앱에서는 선생님이 사이드바를 클릭한 직후 사이드바(맨 앞 프로그램)가 부르므로 더 유리하다.
2. **창 제목 형식** (맥과 다름):
   - 파워포인트·엑셀: 확장자까지 붙은 파일 이름 + 프로그램 이름 ("샘플_발표자료.pptx - PowerPoint"). 맥은 확장자 없음. 파일 이름이 들어 있는지로 짝지으므로(`findByTitle`) 둘 다 맞았다.
   - 한글 빈 문서: "빈 문서 1 - 한글"
   - 한글 파일: **"파일이름.hwp [폴더 전체 경로\] - 한글"** — 폴더 경로가 제목에 들어간다. 경로에 윈도우 사용자 이름이 들어갈 수 있으므로 한글 창 제목은 기록·공유하지 않는다. 같은 이름의 파일이 다른 폴더에 있어도 경로로 구분할 수 있다
   - 한글이 이미 다른 문서를 열고 있으면 같은 한글 프로그램 안에 **새 창**(다른 창 번호)으로 연다. 실행기는 자기가 연 창만 닫았고 선생님 문서 창은 그대로 남았다
   - 크롬 "… - Chrome", 웨일 "… - Whale", 엣지 "… - (프로필 이름) - Microsoft Edge"
   - **엣지 제목의 "Microsoft"와 "Edge" 사이에 보이지 않는 글자(폭 없는 공백, U+200B)가 들어 있다.** 창 제목으로 프로그램을 구분하면 안 되고, 실행 파일 이름(`msedge.exe`)으로 구분한다.
3. **브라우저는 창을 닫아도 뒤에서 계속 실행된다** (크롬·엣지). 그래서 실행기의 로컬 파일 제공(127.0.0.1)이 브라우저 연결을 기다리며 끝나지 않았다 → 끝낼 때 연결까지 끊도록 실행기를 고쳤다 (`closeAllConnections`). 실제 앱도 수업을 끝낼 때 같은 처리가 필요하다.
4. **꺼져 있던 브라우저를 `--new-window`로 켜면**: 크롬·웨일은 요청한 창 하나만 열렸다. 엣지는 첫 창에 탭이 하나 더 붙었다 (제목 "수업 사이드바 시험 A 외 페이지 1개"). 엣지의 시작 페이지로 보인다. 이전 창들이 한꺼번에 복원되지는 않았다.
5. **프로그램 열기**: 윈도우는 `cmd`의 `start`(ShellExecute)로 연다. 브라우저는 App Paths에 등록된 이름(`chrome.exe`, `msedge.exe`, `whale.exe`)으로 찾고, 한글은 App Paths에 없어 `.hwp` 파일 연결(`assoc`/`ftype`)에서 실행 파일을 찾았다. 이렇게 연 브라우저는 실행기가 끝나도 계속 살아 있다 (실행기와 떨어진 독립 프로그램).
6. **좌표**: 도우미를 Per-Monitor DPI Aware V2로 설정해 물리 픽셀로 주고받는다. 윈도우 10·11 창에는 보이지 않는 그림자 테두리(약 7픽셀)가 있어서, `SetWindowPos`에 그대로 넣으면 창이 7픽셀 안쪽으로 들어간다. 도우미가 그림자 폭만큼 보정해 보이는 테두리가 요청 위치에 오게 했다 (배치 결과 오차 0).
7. **최소 폭**: 크롬 최소 폭은 배율 100%에서 약 500픽셀, 배율 200% 화면에서 1004 물리 픽셀. 즉 배율을 반영한 약 500이 기준이다 (맥 500포인트와 같다). 분할 계산은 물리 픽셀로 하되, 최소 폭은 배율을 곱해 생각해야 한다.
8. **배율이 다른 화면으로 창을 옮기면 한 번에 안 맞는다.** 창이 새 배율에 맞춰 스스로 크기를 바꾸기 때문이다 (`WM_DPICHANGED`). 도우미가 옮긴 뒤 다시 읽어 어긋나면 한 번 더 맞춘다. 실제 앱도 이 방식을 그대로 쓴다.
10. **외부 모니터를 뺐다 다시 꽂기** (`node runner/replug.js`, 선생님과 함께, 2026-11-21). 학생 화면 왼쪽 반에 크롬 창을 놓고 시험했다.
    - 뺄 때: 도우미가 모니터가 빠진 것을 바로 알아챘고, 윈도우가 창을 노트북 화면 왼쪽 위(0,0)로 옮겼다. 배율이 200% → 100%로 바뀌어 크기도 절반(637×751)이 됐다. 0.6초 안에 자리 잡음. 창은 최소화되지 않고 살아 있었다.
    - 다시 꽂을 때: **윈도우가 창을 학생 화면의 원래 자리 근처로 스스로 되돌려 놓았다** (-2549,0 1280×1493, 원래 -2560,0 1280×1504에서 11픽셀 어긋남). 정확하지 않으므로 사이드바가 다시 놓아야 한다.
    - **다시 꽂은 직후 몇 초 동안은 학생 화면의 작업 표시줄이 아직 없어서, 사용 영역이 화면 전체(높이 1600)로 읽혔다.** 그때 다시 놓은 창은 높이 1600이 되어 나중에 생긴 작업 표시줄(96)에 가려진다. 조금 뒤 다시 읽으니 1504로 돌아왔다. → 실제 앱은 모니터가 다시 연결되면 바로 한 번 놓고, 사용 영역이 바뀌는 신호(Electron `display-metrics-changed`의 `workArea`)가 오면 한 번 더 놓아야 한다.
12. **저장 여부를 묻는 창(모달)이 떠 있을 때 닫기** (`node runner/modal.js`, 자동, 엑셀로 시험):
    - 고친 문서에 닫기 요청(`WM_CLOSE`)을 보내면 창이 닫히지 않고 "Microsoft Excel" 저장 창이 뜬다. **저장 창은 2.5초 넘게 걸려서 떴다** → 닫기를 보낸 뒤 몇 초 동안은 "닫히는 중"으로 보고 기다려야 한다.
    - 저장 창이 떠 있는 동안 닫기 요청을 한 번 더 보내도 아무 일도 없다 (창 그대로, 저장 창이 또 생기지 않음). 맥과 같다.
    - 저장 창이 떠 있으면 바탕 창이 "사용 안 함" 상태가 된다. 도우미 `list`가 이것을 보고 창마다 **`waiting`(답을 기다리는 창 번호·제목)**을 알려 준다 — 맨 앞이 아니어도 알 수 있다. 1차 시험에서는 맨 앞 창만 보고 판단해 놓쳤다가 이렇게 고쳤다.
    - 바탕 창을 앞으로 가져오기(`raise`)하면 윈도우가 저장 창을 함께 앞으로 가져온다. 사이드바는 "답을 기다리는 창이 있습니다"를 표시하고 그 창을 앞으로 가져오면 된다.
13. **관리자 권한 프로그램**: 실행기가 메모장을 관리자 권한으로 열려고 했더니(`Start-Process -Verb RunAs`) 1분 안에 창이 열리지 않았고, 허용 창도 남아 있지 않았다. 원인은 확인하지 못했다 (윈도우는 뒤에 있는 프로그램의 요청이면 허용 창을 작업 표시줄에서만 깜빡이게 하는 경우가 있다). 사이드바가 관리자 권한이 필요한 프로그램을 직접 여는 일은 피한다. 관리자 권한 창을 옮기거나 닫을 수 있는지는 아직 확인하지 못했다 (`node runner/elevated.js` — 선생님이 명령 프롬프트를 관리자 권한으로 열면 그 창으로 시험).
14. **꺼졌다 켜진 브라우저는 마지막으로 창을 닫은 화면에 새 창을 연다.** 앞 시험에서 학생 화면에 있던 크롬 창을 닫았더니, 다음 새 창이 학생 화면에 열렸다. 수업 중에는 준비되지 않은 창이 학생에게 잠깐 보일 수 있다. 사이드바가 새 창을 찾는 즉시(1.4초 안) 정해진 화면으로 옮기면 되지만, 계획서의 "모두 미리 열기"를 수업 전에 하는 편이 안전하다.
15. **"연결 프로그램 선택"(`OpenWith.exe`, "이 파일을 어떻게 여시겠어요?") 창이 맨 앞에 떠 있으면 어떤 창도 앞으로 가져오지 못한다** (2026-11-22, 설치판 시험 중 발견). 도우미의 세 방법(보통·빈 입력·입력 연결)이 모두 실패하고 2.4초 뒤 `ok:false`, 맨 앞은 그대로 그 창. 설치판 도우미와 개발용 도우미가 똑같았다 (설치판 문제 아님). 창 열기·⇄·닫기는 그대로 됐다 (앞으로만 안 됨). 이 창은 08:45부터 내장 화면에 떠 있었고 누가 띄웠는지는 모른다 (Claude가 연 창인지 확실하지 않아 닫지 않음). 사이드바에서 열린 자료를 다시 누르면 "맨 앞으로 가져오지 못했습니다" 안내가 나와야 하는데, 처음에는 창이 없어진 것으로 잘못 알고 같은 자료를 한 번 더 열었다 (아래 "윈도우 설치판" 6). 수업 중에 이런 창이 뜨면 선생님이 먼저 닫아야 한다 → #21에서 다시 열지 않고 "앞에 떠 있는 '연결 프로그램 선택' 창을 먼저 닫은 뒤 다시 눌러 주세요"로 안내하게 고침 (아래 "앞으로 못 가져올 때 같은 자료를 다시 열던 문제").

체험판을 윈도우에서 돌리려고 고친 것:
1. **도우미 부르기**: 윈도우는 `node poc/win-helper/winctl.js` 대신 **Electron 자신을 Node로 실행**한다 (`ELECTRON_RUN_AS_NODE=1`). 따로 Node를 설치하지 않아도 되고, koffi가 그대로 불러와졌다. 한 번 부르는 데 약 0.08초로 Node와 같다. `watch`도 같은 방법.
2. **사이드바 폭 단위**: 윈도우 도우미는 물리 픽셀이므로 사이드바 폭(280, Electron 화면 단위)에 교사 화면 배율을 곱해 뺀다. 교사 화면이 150%면 420픽셀. (맥은 포인트라 그대로)

    - 고침: 닫기 요청 뒤 1초쯤 지나도 창이 남아 있으면 앞으로 가져와 프로그램이 묻게 하고, 도우미 `list`의 `waiting`이 보이는 즉시 "답을 기다립니다"로 표시한다 → **2.4초**. 평범한 닫기는 0.6초 안에 끝나 앞으로 가져오는 일이 없다. (맥 도우미는 `waiting`이 없어 전처럼 2.4초 뒤 판단)
    - 시험할 때: 저장 창에 Enter 키를 보내도 안 먹힐 때가 있었다. UI 자동화(UIAutomation)로 "저장 안 함" 단추를 누르는 편이 확실했다 (단추 이름·문구로 예시 파일인지 확인한 뒤).
14. **메모장 탭 보호** (체험판 8): 사이드바는 탭을 쓰는 프로그램(윈도우 메모장)의 창을 **사이드바가 새로 만든 창이고, 지금 보이는 탭이 그 메모일 때만** 닫는다. 열기 전부터 있던 창에 탭으로 열렸거나, 다시 켰을 때 다시 연결한 창이거나, 앞에 보이는 탭이 다른 파일이면 창을 닫지 않고 연결만 풀며 "메모장에서 이 탭만 닫아 주세요"라고 알린다. 단위 테스트 3개로 확인. 선생님 메모장 창이 열려 있어 실제 탭 상황은 시험하지 않았다 (메모장이 다른 탭을 뒤에 둔 채 메모 탭을 앞에 보이고 있으면 여전히 함께 닫힐 수 있다 — 윈도우 11 메모장은 다음에 켤 때 탭 내용을 되살린다).
    - 함께 알게 된 것: 다시 켰을 때 다시 연결은 창 제목의 파일 이름으로 찾으므로, 다른 폴더(다른 사이드바)에서 연 같은 이름의 메모장 창도 연결됐다. 메모장 제목에는 폴더가 없어 구분할 수 없다 → 위 보호 덕분에 그 창을 닫지는 않는다.

### 선생님 확인과 요청 기능 셋 (2026-11-22, 브랜치 `win/sidebar-options`)
15. **선생님 확인**: 선생님이 이 PC(노트북 + 외부 모니터 MB16NCG 200%)에서 체험판(#9·#14)을 직접 써 보고 "잘 돼요"라고 하셨다. 드린 확인 목록은 접힌 반투명 노란 막대, 왼쪽 끝에 마우스를 대면 펼침, PPT가 학생 화면에 열림, 슬라이드 쇼 위 사이드바, 메모장 탭 시험(선생님이 연 메모장에 진행 메모가 탭으로 열리고 ✕를 누르면 창은 안 닫히고 "이 탭만 닫아 주세요"), 모니터 뺐다 꽂기(선택). **어느 항목까지 해 보셨는지는 따로 여쭙지 않았다.** 그러면서 기능 세 가지를 요청하셨다 (아래 16~18).
16. **메모장 탭을 사이드바에서 닫기** (도우미 `closetab`·`findtab`, `poc/win-helper/README.md`):
    - 이 PC의 메모장(11.2609)은 꺼져 있다가 켜질 때 **지난번 탭을 되살린다**. 그래서 사이드바가 메모장을 새로 켜도 그 창에 선생님 탭이 함께 있을 수 있다 → 탭을 쓰는 메모장은 **창 닫기(WM_CLOSE)를 쓰지 않고 진행 메모 탭만 닫는다.** 사이드바가 연 창이면 ✕로 바로, 열기 전부터 있던 창(선생님 메모장)이나 다시 켰을 때 연결한 창이면 안내 옆 "사이드바에서 이 탭만 닫기" 단추로 (같은 이름의 다른 폴더 파일일 수 있어 선생님이 누를 때만).
    - **처음 방법(키보드)은 버렸다**: Ctrl+Tab으로 탭을 넘기며 창 제목이 메모가 될 때 Ctrl+W를 보내려 했다. 첫 Ctrl+Tab에 되살린 탭으로 넘어가자 메모장 안에 "지정된 경로를 찾을 수 없습니다" 알림이 떴고(그 탭의 파일이 그 자리에 없음), 그 뒤로는 키가 먹지 않아 25번 눌러도 탭이 그대로였다. 아무 탭도 닫거나 바꾸지 않았다 (지나간 탭은 모두 "수정되지 않음" 그대로). 알림을 "확인"으로 닫자 메모장이 파일이 없는 탭 2개(수정되지 않은 것)를 목록에서 뺐다 — 저장 안 한 글이 있던 탭 2개는 그대로 남았다.
    - **지금 방법(UI 자동화)**: 메모장 탭은 UI 자동화(화면 읽기 프로그램이 쓰는 윈도우 기능)로 `"파일이름. 수정되지 않았습니다."` 같은 이름의 탭 항목으로 보인다. 이름이 정확히 그 파일인 탭을 골라(Select) 그 탭에 달린 "탭 닫기" 단추를 누른다(Invoke). 키를 쓰지 않아 다른 탭에 글자가 들어갈 일이 없다. 시험용 파일로: 뒤에 있던 탭 닫기 0.8초, 다른 탭 그대로. 한 번 더 부르면 "찾지 못함"(아무것도 안 닫음).
    - **저장 안 한 탭은 닫기 단추 대신 점(●)이 있어 단추가 없다** → 그때만 Ctrl+W(보이는 탭만 닫는 단축키). 보내기 바로 앞에 키보드 초점이 그 메모장 창 안인지, 창 제목이 그 파일인지(`*파일 - 메모장`), 확인 창이 없는지 다시 본다.
    - **메모장의 저장 여부 창은 별도 창이 아니라 창 안의 팝업**("변경 내용을 …에 저장하시겠습니까?" 저장 / 저장하지 않음 / 취소)이라 `list`의 `waiting`(창 사용 안 함)으로는 안 보인다. 팝업 창 안의 `PrimaryButton`·`SecondaryButton`·`CloseButton`으로 찾는다 (탭에 마우스를 올리면 뜨는 설명 팝업도 같은 "Popup"이라 단추로 구분). 시험: 수정한 시험 탭 → 0.8초 만에 "답 기다림", "저장하지 않음"을 누르자 탭만 닫힘, 파일 내용 그대로.
    - UI 자동화는 PowerShell(`-EncodedCommand`)로 부른다. 이 PC는 PowerShell 스크립트 파일 실행이 막혀 있지만(실행 정책) 명령으로 넘기는 방식은 정책과 상관없이 동작했다 (정책은 바꾸지 않음). 한 번에 0.5~0.8초.
    - 체험판에서 (`SIDEBAR_DEBUG`): 선생님 탭 2개가 있는 메모장에 진행 메모가 탭으로 열림(3.7초) → ✕ → 창 안 닫힘·안내와 단추 → 단추 → "탭을 닫았습니다 (메모장의 다른 탭은 그대로)", `findtab`으로 메모 탭 0개·선생님 탭 그대로 확인.
    - 사이드바가 메모장을 새로 켠 창의 ✕는 단위 테스트로만 확인했다 (시험 중 열린 메모장 창에 선생님의 저장 안 한 탭이 있어 그 창을 닫지 않았다). 선생님 확인 항목에 넣었다.

## 윈도우 설치판 (2026-11-22, 브랜치 `win/installer`)
맥 설치판(#13)과 같은 electron-builder 26으로 만든다. 만드는 법은 `app/README.md` "설치판 (윈도우)". 시험은 이 노트북 + 외부 모니터 MB16NCG(200%), 선생님의 개발용 사이드바(`npm start`, 접힌 상태)가 켜져 있는 채로 했다.
1. **만드는 것** (`npm run dist:win`, 이 PC에서 약 3분): `lesson-sidebar-0.1.0-win-setup.exe`(설치 파일, NSIS, 122MB)와 `lesson-sidebar-0.1.0-win-portable.exe`(설치 없이 켜는 파일, 111MB). 둘 다 64비트(x64)만. 앱 폴더는 358MB (대부분 Electron).
   - 설치 파일은 **한 번 누르면 끝나는 방식**(`nsis.oneClick`) + **사용자 폴더 설치**(`perMachine: false`): 묻는 것 없이 `%LOCALAPPDATA%\Programs\lesson-sidebar`에 설치하고 바로 켠다. **관리자 권한 창이 뜨지 않는다.**
   - 실행 파일 이름은 맥처럼 영어 `LessonSidebar.exe`(`build.productName`), 바로 가기·제거 목록 이름은 "수업 사이드바"(`nsis.shortcutName`·`uninstallDisplayName`). 설치 프로그램의 물음 창은 안쪽 이름을 써서 "LessonSidebar을(를) 제거 하시겠습니까?"처럼 나온다.
   - 맥 전용 `extraResources`(맥 도우미 `winctl`, `ko.lproj`·`en.lproj`)는 `build.mac.extraResources`로 옮겼다 (윈도우 빌드에서 맥 도우미 파일을 찾다 멈추지 않게. 맥 결과물은 같아야 함 — 맥 자동 검사로 확인).
2. **도우미 넣기**: `poc/win-helper/winctl.js`·`package.json`(`"type": "module"`)과 `node_modules/koffi`·`node_modules/@koromix/koffi-win32-x64`(koffi 3은 운영체제별 바이너리가 따로 있는 꾸러미)를 `resources/win-helper`에 (3MB). electron-builder는 복사 원본의 맨 위 `node_modules` 폴더를 빼 버려서, `node_modules`를 따로 원본으로 잡아 복사한다. 앱은 원래대로 `process.resourcesPath\win-helper\winctl.js`를 자기 실행 파일 + `ELECTRON_RUN_AS_NODE=1`로 돌린다 (`main.js`의 `makeHelper()`는 고칠 것 없었음). Electron fuses는 설정하지 않아 `RunAsNode`가 켜진 그대로다.

## 앞으로 못 가져올 때 같은 자료를 다시 열던 문제 (2026-11-22, 브랜치 `win/raise-notfront`)
1. **문제** (설치판 시험 `win/installer`에서 발견, 개발용도 같음): 열린 자료를 다시 눌렀을 때 맨 앞으로 못 가져오면 사이드바가 "창이 닫혀 있어 다시 엽니다"로 **같은 자료를 한 번 더 열었다.** 처음 창은 사이드바와 연결이 끊긴 채 남는다. 그때 화면에 "연결 프로그램 선택"(`OpenWith.exe`) 창이 맨 앞에 떠 있어 어떤 창도 앞으로 오지 않았다. 원인: 도우미 `raise`는 창이 있어도 맨 앞이 안 되면 `{"ok":false, front, detail}`로 답하는데, `Helper.call`이 `ok:false`를 오류로 바꾸고 `Session.raiseWid`가 모든 오류를 "창 없음"으로 봤다.
2. **고친 것** (공통 코드 `app/src/core/session.js`·`helper.js`):
    - 앞으로 가져오기가 오류면 도우미 `list`로 그 창이 아직 있는지 본다. **있으면 다시 열지 않고** "맨 앞으로 가져오지 못했습니다" 안내, 없으면 예전처럼 다시 연다. 목록도 못 읽으면 예전처럼 "창 없음"으로 본다.
    - `Helper.call`은 `ok:false` 응답을 오류의 `response`에 붙인다 (오류 글은 그대로). 사이드바는 그 안의 `front`(그때 맨 앞 창)로 **"앞에 떠 있는 '연결 프로그램 선택' 창을 먼저 닫은 뒤 다시 눌러 주세요"**라고 알린다. 맨 앞 창 이름은 제목(30자까지) → 없으면 프로그램 이름(`OpenWith.exe`만 "연결 프로그램 선택"으로 바꿈). 맨 앞이 사이드바 자신이거나 이름을 모르면 "앞을 가리는 창(확인 창 등)이 있으면 먼저 닫은 뒤 다시 눌러 주세요".
    - 그 창이 저장 여부 등 답을 기다리는 중이면(`list`의 `waiting`) 예전처럼 "답 기다림"으로 표시한다.
    - 다른 곳의 앞으로 가져오기(열기 직후, ⇄, 나란히, 모두 미리 열기, 닫는 중)는 결과를 쓰지 않아 동작이 같다. 실패할 때만 목록을 한 번 더 읽는다 (약 0.1초).
    - 단위 테스트 6개 추가 (`app/test/session.test.js` 4개, `app/test/helper.test.js` 2개) → 체험판 테스트 58개 통과.
3. **실제 도우미로 재현** (이 PC, 개발용 도우미 + 실제 `Session`을 화면 없이 Node로. 선생님의 개발용 사이드바가 켜져 있어 체험판을 하나 더 켜지는 않았다 — 두 번째 사이드바는 바로 꺼짐): Claude가 띄운 시험 창(PowerShell 창 하나)을 자료로 연결하고
    - 막기 전: "앞으로 가져왔습니다" 0.09초.
    - `OpenWith.exe <시험 파일>`로 "연결 프로그램 선택" 창을 띄우면 뒤에서 실행해도 그 창이 맨 앞을 차지한다. 도우미 `raise`는 세 방법 모두 실패해 2.3초 뒤 `ok:false`, `front.app`은 `OpenWith.exe`, 제목은 빈 글자. **이 창은 도우미 `list`에 나오지 않는다** (`front`에만 보임). (`rundll32 shell32.dll,OpenAs_RunDLL`로는 창이 뜨지 않았다.)
    - 사이드바: 2.5초 뒤 "'시험 창'을(를) 맨 앞으로 가져오지 못했습니다. 앞에 떠 있는 '연결 프로그램 선택' 창을 먼저 닫은 뒤 다시 눌러 주세요" — **다시 열기 0번, 처음 창과 연결 그대로.**
    - 그 창에 정상 닫기 요청(`WM_CLOSE`)을 보내면 바로 닫혔고, 다시 누르자 "앞으로 가져왔습니다" 0.09초.
    - 시험 창·연결 프로그램 선택 창·시험 파일은 모두 닫고 지웠다.
4. 맥: 공통 코드라 맥 도우미가 `raise`에서 `ok:false`로 답할 때도 같은 길을 탄다. 맥 도우미가 그런 답에 `front`를 넣지 않아도 `list`로 판단하므로 다시 열지는 않는다 (안내에 앞 창 이름만 빠짐). 맥 확인은 맥 Claude에게 넘김 (`HANDOFF.md` "넘길 일").

1. **전체 실행**: 예시 수업 + 링크 3개(유튜브, 없는 페이지, 없는 구글 문서) → 점검 14개 2.4초. 파워포인트·엑셀·한글·메모장 "있음", 크롬에서 엶, 유튜브 "공개 영상", 없는 페이지·없는 구글 문서 "페이지가 없습니다", 모니터 1개 주의, 창 제어 권한 허용됨(윈도우는 늘), 저장 공간. 맥에서 만든 판단이 윈도우에서도 그대로 맞다.
2. **프로그램이 있는지** (`launcher.appInstalled` → `assocExe`): 확장자 연결(`assoc`/`ftype`)에서 실행 파일을 찾아 실제로 있는지 본다. 하나에 약 0.1초. 이 PC에서 `.pptx`·`.xlsx`·`.hwp` 모두 있음. 없는 확장자(한글이 없는 PC와 같음)는 `false` → "한글이 이 PC에 없습니다 · 한글 뷰어…"가 나온다 (판단 자체는 단위 테스트에도 있음). 한글을 지운 PC로 직접 시험하지는 않았다.
   - 고침: 연결이 없을 때 `cmd`가 내는 오류 글(한국어 CP949)이 깨진 글자로 앱 기록에 새어 나왔다 → 버림 (실패는 종료 코드로 앎).
   - 남은 빈틈: `.hwp`가 "한글 뷰어"에 연결된 PC는 "있음"으로 나오지만, 사이드바는 한글 창(`Hwp.exe`)을 찾으므로 열고 나서 창을 못 찾을 수 있다 (뷰어 실행 파일 이름을 몰라 고치지 않음). 이 PC는 `.docx`가 한컴 워드에 연결되어 있다 (워드 파일은 원래 "기본 프로그램"으로 열어 상관없음).
3. **구글 드라이브 폴더 알아보기** (`precheck.cloudOf`): 이 PC는 구글 드라이브가 `G:` 드라이브이고 맨 위에 "내 드라이브", "공유 드라이브", "다른 컴퓨터"가 있다. "내 드라이브"만 알아보고 **공유 드라이브(학교에서 함께 쓰는 드라이브)·다른 컴퓨터·바로 가기로 넣은 폴더(`.shortcut-targets-by-id`)는 몰랐다** → 드라이브 맨 위에 그 이름이 있으면 구글 드라이브로 본다 (아무 폴더 속의 "공유 드라이브"는 아님). 단위 테스트 5줄 추가. 구글 드라이브 안의 파일을 실제로 읽어 받는 것(스트리밍)은 선생님 드라이브라 시험하지 않았다.
4. **학교 프록시**: 링크 확인은 Electron `net.fetch`(이 PC의 인터넷 설정을 따름)라 학교에서 확인해야 한다 (남음).

### 수업 꾸러미
5. **윈도우 탐색기 "압축(zip) 폴더"로 묶은 zip**: 탐색기와 같은 셸 기능(`Shell.Application` → `CopyHere`)으로 예시 수업을 묶었다. 이 PC(윈도우 11)의 탐색기는 한글 이름을 **UTF-8 표시 없이 CP949로** 적었다 → 사이드바가 바른 이름으로 읽어 가져옴 (같은 수업이 있어 "사본", 1.4초, 파일 7개, 이름에 "(사본)"·새 수업 번호). 탐색기 zip에는 `.sidebar`(잠금·백업)도 들어가는데 가져올 때 뺀다. 잠금 파일 이름에 컴퓨터 이름이 들어 있으니 탐색기로 묶은 zip을 공개된 곳에 올리지 않는다.
6. **맥 Finder "압축"으로 묶은 zip**: 맥이 없어 단위 테스트로 — 한글 이름이 자모로 나뉜 NFD + UTF-8 표시 없음 + `__MACOSX`·`.DS_Store` → 윈도우에서 바른 이름(NFC)으로 풀리고 `__MACOSX`·`.DS_Store`는 빠진다. 맥 사이드바가 만든 꾸러미는 이미 NFC + UTF-8 표시라 윈도우가 만든 것과 같다.
7. **윈도우 사이드바가 만든 꾸러미를 탐색기로 풀기**: 한글 폴더·파일 이름이 모두 바르게 풀렸다 (탐색기가 UTF-8 표시를 읽음).
8. **덮어쓰기 때 수업 파일이 열려 있으면 — 고침.** 수업의 발표 자료를 파워포인트로 열어 둔 채 "덮어쓰기"를 골랐더니:
   - 윈도우는 안에 열린 파일이 있는 폴더의 이름을 바꾸지 못한다 (`EPERM`). 파워포인트처럼 "쓰기 금지"로 잡은 파일뿐 아니라 평범하게 열어 둔 파일 하나도 막는다.
   - 고치기 전: 선생님께 `EPERM: operation not permitted, rename '…폴더 전체 경로…'` 영어 오류가 그대로 보였고(경로에 사용자 이름이 들어갈 수 있음), 보관함에 **`.가져오는 중-…` 임시 폴더가 지워지지 않고 남았다** (구글 드라이브 보관함이면 이것까지 올라감). 원래 수업은 그대로였다.
   - 고친 뒤 (`app/src/core/bundle.js`): ① 풀기 전에 덮어쓸 수업의 파일을 하나씩 쓰기로 열어 보아(내용은 안 바꿈) 막히면 바로 멈춘다 → 0.4초 만에 **"'04_발표자료.pptx' 파일이 다른 프로그램(파워포인트·엑셀·한글·탐색기 등)에 열려 있어 덮어쓰지 못했습니다 · 그 파일을 닫고 다시 가져오거나 "사본으로 가져오기"를 고르세요 (지금 수업은 그대로입니다)"**. 파일 7개 확인에 18밀리초. 맥은 이 확인을 하지 않는다. ② 그래도 바꿔치기가 막히면(평범하게 열린 파일 등) 0.4초씩 4번까지 다시 해 보고(클라우드 동기화가 잠깐 잡은 경우), 안 되면 임시 폴더를 지우고 같은 안내(이름을 모르면 "이 수업 폴더의 파일이")를 낸다. "사본" 가져오기의 마지막 이름 바꾸기도 실패하면 임시 폴더를 지운다. ③ 준비 화면에서 보던 수업을 덮어쓰다 실패하면 그 수업을 다시 연다 (`main.js`, 전에는 빈 화면이 됨).
   - 시험: 파워포인트를 연 채 → 위 안내, 임시 폴더·백업 폴더 없음, 준비 화면에 수업 그대로. 파워포인트를 닫고(정상 닫기 요청) 다시 → 덮어쓰기 성공, 예전 수업은 `.sidebar/덮어쓰기 전/`에. 단위 테스트 1개(윈도우만: 파일 하나를 열어 둔 채 덮어쓰기 → 안내·임시 폴더 없음·수업 그대로 → 닫은 뒤 성공) + 맥 Finder zip 1개 → 체험판 테스트 66개 통과.

## 맥 기능 윈도우 확인 (2026-11-22, 브랜치 `win/mac-features`, 0.2.0)
맥에서 만든 기능(#25~#32)을 개발용 체험판(시험용 설정 폴더 + 원격 조작, 예시 수업 복사본)으로 이 노트북에서 켜 보았다. **외부 모니터는 빠진 상태(내장 화면 100% 한 대)**라 배율이 다른 학생 화면에서의 위치는 선생님과 함께 볼 일로 남겼다. 맥 Claude 방식대로 기능마다 설치판을 만들지 않았다 (PR의 윈도우 자동 검사가 설치판 만들기·켜 보기를 한다).

고친 것:
1. **고정해 둔 동안 계속 비키기를 윈도우에도 켬** (`main.js` `ASIDE_KEEP = ASIDE_OK`). 맥에서 선생님이 "비키기가 안 된다"고 하신 것과 같은 기대라서. 2초마다 창 목록 한 번(약 0.08초). 시험: 시험 크롬 창을 사이드바 아래(50,100)로 옮기면 2초 안에 280,100으로, 최대화하면 사이드바 오른쪽 전체(280,0 1640×1032)로, 설정을 끄면 돌려놓음. 윈도우 스냅으로 붙인 창도 왼쪽 끝이 사이드바 아래면 옮겨진다.
   - 함께 고침 (`session.js` `keepAside`): 고정해 둔 동안 선생님이 **최대화**한 창은 설정을 끄거나 자동 숨김으로 바꿀 때 예전 크기가 아니라 **다시 최대화**로 돌려놓는다 (고치기 전에는 처음 크기 900×700으로 돌아감). 맥은 최대화가 없어 그대로. 단위 테스트 1개.
2. **나란히 보기 조절 바가 8픽셀 비켜 서 있던 것** (`main.js` `placeDivider`): 조절 바 창을 16픽셀 폭으로 놓는데 **윈도우는 창을 32픽셀(세로 막대) · 39픽셀(가로 막대)보다 좁게 만들지 않아**(체험판 6의 접힌 사이드바와 같은 문제), 왼쪽 끝은 맞고 가운데 줄이 경계보다 8픽셀 오른쪽에 그려지고, 오른쪽 창 가장자리 16픽셀을 눌러도 바가 받았다. → 창이 넓어졌으면 경계에 가운데를 맞추고, 누르는 자리는 창 모양(`setShape`)으로 가운데 16픽셀만 남긴다 (바깥은 원래 투명해서 그리기가 잘리지 않아도 보이는 것은 같다). 시험: 반반 배치 경계 x=1100 → 바 창 1084~1116, 1093·1100·1107은 바, 1112는 오른쪽 크롬, 1088은 왼쪽 크롬. 3개 배치(큰 화면 + 작은 2개)의 가로 막대도 경계 y=516에서 509~523만 바. 배율 200% 학생 화면에서는 선생님과 함께 확인.
3. **원드라이브 충돌 사본** (`reuse.js` `findConflicts`): 원드라이브는 충돌하면 `lesson-<PC 이름>.json`을 만든다 (PC 이름을 알 수 없어 실제 충돌은 만들지 않음). 수업 폴더 맨 위의 `lesson-…`·`lesson_…`·`lesson …`·`lesson(1)` 모양이면서 수업 파일(schema 1)인 것을 사본으로 본다 — 사이드바가 맨 위에 `lesson-….json`을 만드는 일은 없다(백업은 `.sidebar/backup/`). 단위 테스트 1개 (원드라이브·구글 드라이브·드롭박스 모양, 수업 파일이 아닌 것·다른 이름은 건너뜀).

그 밖에 알게 된 것:
4. **크롬 업데이트 대기 중 겹쳐 뜨기** (맥 `docs/poc/mac.md` 28): 지금 이 PC 크롬은 업데이트 대기 상태가 아니라(실행 중 157.0.8103.79 = 디스크) 재현하지 못했다. 윈도우 크롬은 `chrome.exe`가 작은 시작 파일이고 버전별 폴더가 나란히 있어, 켜진 크롬이 있으면 새 실행은 같은 프로필의 켜진 크롬에 요청을 넘기고 끝난다 (맥은 `open -n`으로 새 프로그램을 억지로 하나 더 띄워서 생긴 문제). 그래서 윈도우는 `browserState`를 `{ running: null }` 그대로 둔다. 크롬 오른쪽 위에 "업데이트" 표시가 뜬 날 한 번 확인하면 좋다.
5. **한글 저장 창에 닫기 요청 두 번** (`runner/modal.js --app=hwp`, 맥 부탁): 윈도우 한글은 첫 닫기 요청 0.1초 뒤 저장 창이 `waiting`에 보이고, 한 번 더 보내도 **저장 창이 더 생기지 않았다** (같은 창 번호). 맥 한글과 다르다. 앞으로 가져오기도 됨.
6. 같은 시험을 엑셀로 두 번 돌리니 이번에는 저장 창 없이 4.5~5.2초에 엑셀이 닫혔다 (2026-11-21에는 저장 창이 떴음). 시험이 넣은 글자가 엑셀에 들어가지 않은 것으로 보이나 원인은 확인하지 못했다 (사이드바 동작과는 상관없음).

|---|---|---|
| 컴퓨터 전체가 느려지고 포인터가 끊김 | **학생 화면 미리보기**가 0.5초마다 `desktopCapturer.getSources`로 화면을 새로 찍었다. 윈도우는 찍을 때마다 화면 복제(DXGI)를 새로 시작해 체험판이 코어 하나의 **53%**를 계속 썼다 (미리보기를 끄면 0%) | 윈도우만: 사이드바 화면이 학생 화면을 영상(`getUserMedia` desktop, 폭 528, 초당 2장)으로 한 번 받아 `<video>`로 보임 → **1%**. 맥은 그대로 (정지 중 창 쌓기 그림) |

그 밖에:
- 처음 켠 체험판이 확대·캡처 핀을 쓰는 중 **저절로 꺼졌다 (종료 코드 29)**. 직전 기록은 화면 찍기 실패(`0x887A0026`, DXGI 접근 끊김)뿐. 원격으로 확대·핀을 20번 넘게 켜고 꺼도, 선생님이 다시 써 봐도 재현되지 않아 **원인 모름**. 미리보기를 영상 방식으로 바꾼 뒤로는 화면 찍기 실패 기록도 나오지 않았다.
- 마이크 목록은 이름까지 나온다 (`enumerateDevices`, 권한을 따로 묻지 않음). 컴퓨터 소리는 스피커를 고를 수 없다 (Electron은 기본 출력의 소리만 받음).

### 휴대폰 리모컨 (안드로이드 휴대폰 + Chrome)
- 처음에 휴대폰이 연결되지 않았다. PC는 와이파이 주소에서 기다리고 있었고(그 PC에서는 접속됨), 윈도우 방화벽에도 Electron 허용 규칙이 있었다. 그런데 휴대폰의 접속 시도가 PC에 **한 번도 오지 않았다** (포트를 0.1초마다 지켜봄). 휴대폰 핫스팟으로 바꿔도 같았다.
- 휴대폰 화면: "웹페이지가 일시적으로 다운되었거나 새 웹 주소로 완전히 이동했을 수 있습니다".
- **원인: 휴대폰 Chrome의 '주변 기기' 권한이 꺼져 있었다.** 설정 → 애플리케이션 → Chrome → 권한 → 주변 기기 → 허용 하니 바로 연결됐다. 공유기·방화벽·V3가 아니었다.
- 함께 고친 것: 와이파이를 바꾸면(핫스팟 ↔ 집) QR이 옛 주소를 그대로 보여 휴대폰에서 "연결을 거부했습니다"가 났다 → 리모컨이 켜져 있는 동안 3초마다 주소를 보고 바뀌면 QR을 새로 만든다 (`watchNet`). QR 아래 "연결이 안 되나요?" 접는 안내(주변 기기 권한, 같은 와이파이, 보안 Wi-Fi·VPN, 학교 와이파이 → 핫스팟)를 넣었다.
- 선생님 요청으로 이런 문제와 해결을 **`docs/help/troubleshooting.md`**에 도움말 재료로 모은다.
