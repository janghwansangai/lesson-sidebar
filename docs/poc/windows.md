## 실행기가 예시 파일의 복사본을 열게 바뀐 뒤 (#8, 2026-11-21)
`node runner/run.js --only=P0,P1,F,P5,P6` (외부 모니터 연결): **통과 7 · 실패 0**. 파워포인트·엑셀·한글 모두 `poc/out/copies/`의 복사본(`F1_시각_샘플_….pptx` 등)으로 열기·앞으로·학생 화면 반쪽 배치·닫기가 맞았다.
- 오피스가 복사본을 "보호된 보기"로 열지 않았다 (예시 파일에 인터넷에서 받은 표시(Zone.Identifier)가 없음). 인터넷에서 받은 파일이면 보호된 보기로 열릴 수 있으니, 실제 앱에서 선생님이 받은 파일을 쓸 때는 따로 확인해야 한다.
- 창을 모두 닫은 뒤 복사본이 지워졌다 (`poc/out/copies/`가 비어 있음).
- 한글은 선생님 문서(`123.hwp`)가 열려 있는 상태에서도 복사본을 새 창으로 열었다.

## 알게 된 것

1. **앞으로 가져오기**: 명령줄 도우미가 보통 방법(`SetForegroundWindow`)으로 바로 창을 앞으로 가져왔다.
   - 아무도 키보드·마우스를 만지지 않을 때: 0.05초 (실행기 P2)
   - **선생님이 메모장에 글자를 치는 도중** (`raise-lock.js`, 맨 앞: 메모장): 0.06초, 보통 방법으로 성공. 윈도우의 포커스 가로채기 방지가 이 경우에도 막지 않았다. 이 PC의 포커스 잠금 시간(`ForegroundLockTimeout`)은 기본값 200초
   - 다른 PC·학교 PC에서는 막힐 수 있어서, 도우미는 막히면 ① 빈 마우스 입력을 보낸 뒤 다시 시도(PowerToys와 같은 방법) ② `AttachThreadInput` 순서로 자동으로 이어서 시도하고, 어느 방법이 통했는지 `detail.method`에 남긴다. 실제 앱에서는 선생님이 사이드바를 클릭한 직후 사이드바(맨 앞 프로그램)가 부르므로 더 유리하다.
2. **창 제목 형식** (맥과 다름):
   - 파워포인트·엑셀: 확장자까지 붙은 파일 이름 + 프로그램 이름 ("샘플_발표자료.pptx - PowerPoint"). 맥은 확장자 없음. 파일 이름이 들어 있는지로 짝지으므로(`findByTitle`) 둘 다 맞았다.
   - 한글 빈 문서: "빈 문서 1 - 한글"
   - 한글 파일: **"파일이름.hwp [폴더 전체 경로\] - 한글"** — 폴더 경로가 제목에 들어간다. 경로에 윈도우 사용자 이름이 들어갈 수 있으므로 한글 창 제목은 기록·공유하지 않는다. 같은 이름의 파일이 다른 폴더에 있어도 경로로 구분할 수 있다
   - 한글이 이미 다른 문서를 열고 있으면 같은 한글 프로그램 안에 **새 창**(다른 창 번호)으로 연다. 실행기는 자기가 연 창만 닫았고 선생님 문서 창은 그대로 남았다
   - 크롬 "… - Chrome", 웨일 "… - Whale", 엣지 "… - (프로필 이름) - Microsoft Edge"
   - **엣지 제목의 "Microsoft"와 "Edge" 사이에 보이지 않는 글자(폭 없는 공백, U+200B)가 들어 있다.** 창 제목으로 프로그램을 구분하면 안 되고, 실행 파일 이름(`msedge.exe`)으로 구분한다.
3. **브라우저는 창을 닫아도 뒤에서 계속 실행된다** (크롬·엣지). 그래서 실행기의 로컬 파일 제공(127.0.0.1)이 브라우저 연결을 기다리며 끝나지 않았다 → 끝낼 때 연결까지 끊도록 실행기를 고쳤다 (`closeAllConnections`). 실제 앱도 수업을 끝낼 때 같은 처리가 필요하다.
4. **꺼져 있던 브라우저를 `--new-window`로 켜면**: 크롬·웨일은 요청한 창 하나만 열렸다. 엣지는 첫 창에 탭이 하나 더 붙었다 (제목 "수업 사이드바 시험 A 외 페이지 1개"). 엣지의 시작 페이지로 보인다. 이전 창들이 한꺼번에 복원되지는 않았다.
5. **프로그램 열기**: 윈도우는 `cmd`의 `start`(ShellExecute)로 연다. 브라우저는 App Paths에 등록된 이름(`chrome.exe`, `msedge.exe`, `whale.exe`)으로 찾고, 한글은 App Paths에 없어 `.hwp` 파일 연결(`assoc`/`ftype`)에서 실행 파일을 찾았다. 이렇게 연 브라우저는 실행기가 끝나도 계속 살아 있다 (실행기와 떨어진 독립 프로그램).
6. **좌표**: 도우미를 Per-Monitor DPI Aware V2로 설정해 물리 픽셀로 주고받는다. 윈도우 10·11 창에는 보이지 않는 그림자 테두리(약 7픽셀)가 있어서, `SetWindowPos`에 그대로 넣으면 창이 7픽셀 안쪽으로 들어간다. 도우미가 그림자 폭만큼 보정해 보이는 테두리가 요청 위치에 오게 했다 (배치 결과 오차 0).
7. **최소 폭**: 크롬 최소 폭은 배율 100%에서 약 500픽셀, 배율 200% 화면에서 1004 물리 픽셀. 즉 배율을 반영한 약 500이 기준이다 (맥 500포인트와 같다). 분할 계산은 물리 픽셀로 하되, 최소 폭은 배율을 곱해 생각해야 한다.
8. **배율이 다른 화면으로 창을 옮기면 한 번에 안 맞는다.** 창이 새 배율에 맞춰 스스로 크기를 바꾸기 때문이다 (`WM_DPICHANGED`). 도우미가 옮긴 뒤 다시 읽어 어긋나면 한 번 더 맞춘다. 실제 앱도 이 방식을 그대로 쓴다.
10. **외부 모니터를 뺐다 다시 꽂기** (`node runner/replug.js`, 선생님과 함께, 2026-11-21). 학생 화면 왼쪽 반에 크롬 창을 놓고 시험했다.
    - 뺄 때: 도우미가 모니터가 빠진 것을 바로 알아챘고, 윈도우가 창을 노트북 화면 왼쪽 위(0,0)로 옮겼다. 배율이 200% → 100%로 바뀌어 크기도 절반(637×751)이 됐다. 0.6초 안에 자리 잡음. 창은 최소화되지 않고 살아 있었다.
    - 다시 꽂을 때: **윈도우가 창을 학생 화면의 원래 자리 근처로 스스로 되돌려 놓았다** (-2549,0 1280×1493, 원래 -2560,0 1280×1504에서 11픽셀 어긋남). 정확하지 않으므로 사이드바가 다시 놓아야 한다.
    - **다시 꽂은 직후 몇 초 동안은 학생 화면의 작업 표시줄이 아직 없어서, 사용 영역이 화면 전체(높이 1600)로 읽혔다.** 그때 다시 놓은 창은 높이 1600이 되어 나중에 생긴 작업 표시줄(96)에 가려진다. 조금 뒤 다시 읽으니 1504로 돌아왔다. → 실제 앱은 모니터가 다시 연결되면 바로 한 번 놓고, 사용 영역이 바뀌는 신호(Electron `display-metrics-changed`의 `workArea`)가 오면 한 번 더 놓아야 한다.
12. **저장 여부를 묻는 창(모달)이 떠 있을 때 닫기** (`node runner/modal.js`, 자동, 엑셀로 시험):
    - 고친 문서에 닫기 요청(`WM_CLOSE`)을 보내면 창이 닫히지 않고 "Microsoft Excel" 저장 창이 뜬다. **저장 창은 2.5초 넘게 걸려서 떴다** → 닫기를 보낸 뒤 몇 초 동안은 "닫히는 중"으로 보고 기다려야 한다.
    - 저장 창이 떠 있는 동안 닫기 요청을 한 번 더 보내도 아무 일도 없다 (창 그대로, 저장 창이 또 생기지 않음). 맥과 같다.
    - 저장 창이 떠 있으면 바탕 창이 "사용 안 함" 상태가 된다. 도우미 `list`가 이것을 보고 창마다 **`waiting`(답을 기다리는 창 번호·제목)**을 알려 준다 — 맨 앞이 아니어도 알 수 있다. 1차 시험에서는 맨 앞 창만 보고 판단해 놓쳤다가 이렇게 고쳤다.
    - 바탕 창을 앞으로 가져오기(`raise`)하면 윈도우가 저장 창을 함께 앞으로 가져온다. 사이드바는 "답을 기다리는 창이 있습니다"를 표시하고 그 창을 앞으로 가져오면 된다.
13. **관리자 권한 프로그램**: 실행기가 메모장을 관리자 권한으로 열려고 했더니(`Start-Process -Verb RunAs`) 1분 안에 창이 열리지 않았고, 허용 창도 남아 있지 않았다. 원인은 확인하지 못했다 (윈도우는 뒤에 있는 프로그램의 요청이면 허용 창을 작업 표시줄에서만 깜빡이게 하는 경우가 있다). 사이드바가 관리자 권한이 필요한 프로그램을 직접 여는 일은 피한다. 관리자 권한 창을 옮기거나 닫을 수 있는지는 아직 확인하지 못했다 (`node runner/elevated.js` — 선생님이 명령 프롬프트를 관리자 권한으로 열면 그 창으로 시험).
14. **꺼졌다 켜진 브라우저는 마지막으로 창을 닫은 화면에 새 창을 연다.** 앞 시험에서 학생 화면에 있던 크롬 창을 닫았더니, 다음 새 창이 학생 화면에 열렸다. 수업 중에는 준비되지 않은 창이 학생에게 잠깐 보일 수 있다. 사이드바가 새 창을 찾는 즉시(1.4초 안) 정해진 화면으로 옮기면 되지만, 계획서의 "모두 미리 열기"를 수업 전에 하는 편이 안전하다.
15. **"연결 프로그램 선택"(`OpenWith.exe`, "이 파일을 어떻게 여시겠어요?") 창이 맨 앞에 떠 있으면 어떤 창도 앞으로 가져오지 못한다** (2026-11-22, 설치판 시험 중 발견). 도우미의 세 방법(보통·빈 입력·입력 연결)이 모두 실패하고 2.4초 뒤 `ok:false`, 맨 앞은 그대로 그 창. 설치판 도우미와 개발용 도우미가 똑같았다 (설치판 문제 아님). 창 열기·⇄·닫기는 그대로 됐다 (앞으로만 안 됨). 이 창은 08:45부터 내장 화면에 떠 있었고 누가 띄웠는지는 모른다 (Claude가 연 창인지 확실하지 않아 닫지 않음). 사이드바에서 열린 자료를 다시 누르면 "맨 앞으로 가져오지 못했습니다" 안내가 나와야 하는데, 지금은 창이 없어진 것으로 잘못 알고 같은 자료를 한 번 더 연다 (아래 "윈도우 설치판" 6의 문제). 수업 중에 이런 창이 뜨면 선생님이 먼저 닫아야 한다 — 도우미 `raise` 결과의 `front`(그때 맨 앞 창)를 써서 "앞에 떠 있는 ○○ 창을 먼저 닫아 주세요"로 안내를 바꿀지 검토할 것.

    - 고침: 닫기 요청 뒤 1초쯤 지나도 창이 남아 있으면 앞으로 가져와 프로그램이 묻게 하고, 도우미 `list`의 `waiting`이 보이는 즉시 "답을 기다립니다"로 표시한다 → **2.4초**. 평범한 닫기는 0.6초 안에 끝나 앞으로 가져오는 일이 없다. (맥 도우미는 `waiting`이 없어 전처럼 2.4초 뒤 판단)

14. **메모장 탭 보호** (체험판 8): 사이드바는 탭을 쓰는 프로그램(윈도우 메모장)의 창을 **사이드바가 새로 만든 창이고, 지금 보이는 탭이 그 메모일 때만** 닫는다. 열기 전부터 있던 창에 탭으로 열렸거나, 다시 켰을 때 다시 연결한 창이거나, 앞에 보이는 탭이 다른 파일이면 창을 닫지 않고 연결만 풀며 "메모장에서 이 탭만 닫아 주세요"라고 알린다. 단위 테스트 3개로 확인. 선생님 메모장 창이 열려 있어 실제 탭 상황은 시험하지 않았다 (메모장이 다른 탭을 뒤에 둔 채 메모 탭을 앞에 보이고 있으면 여전히 함께 닫힐 수 있다 — 윈도우 11 메모장은 다음에 켤 때 탭 내용을 되살린다).
    - 함께 알게 된 것: 다시 켰을 때 다시 연결은 창 제목의 파일 이름으로 찾으므로, 다른 폴더(다른 사이드바)에서 연 같은 이름의 메모장 창도 연결됐다. 메모장 제목에는 폴더가 없어 구분할 수 없다 → 위 보호 덕분에 그 창을 닫지는 않는다.

### 선생님 확인과 요청 기능 셋 (2026-11-22, 브랜치 `win/sidebar-options`)
15. **선생님 확인**: 선생님이 이 PC(노트북 + 외부 모니터 MB16NCG 200%)에서 체험판(#9·#14)을 직접 써 보고 "잘 돼요"라고 하셨다. 드린 확인 목록은 접힌 반투명 노란 막대, 왼쪽 끝에 마우스를 대면 펼침, PPT가 학생 화면에 열림, 슬라이드 쇼 위 사이드바, 메모장 탭 시험(선생님이 연 메모장에 진행 메모가 탭으로 열리고 ✕를 누르면 창은 안 닫히고 "이 탭만 닫아 주세요"), 모니터 뺐다 꽂기(선택). **어느 항목까지 해 보셨는지는 따로 여쭙지 않았다.** 그러면서 기능 세 가지를 요청하셨다 (아래 16~18).
16. **메모장 탭을 사이드바에서 닫기** (도우미 `closetab`·`findtab`, `poc/win-helper/README.md`):
    - 이 PC의 메모장(11.2609)은 꺼져 있다가 켜질 때 **지난번 탭을 되살린다**. 그래서 사이드바가 메모장을 새로 켜도 그 창에 선생님 탭이 함께 있을 수 있다 → 탭을 쓰는 메모장은 **창 닫기(WM_CLOSE)를 쓰지 않고 진행 메모 탭만 닫는다.** 사이드바가 연 창이면 ✕로 바로, 열기 전부터 있던 창(선생님 메모장)이나 다시 켰을 때 연결한 창이면 안내 옆 "사이드바에서 이 탭만 닫기" 단추로 (같은 이름의 다른 폴더 파일일 수 있어 선생님이 누를 때만).
    - **처음 방법(키보드)은 버렸다**: Ctrl+Tab으로 탭을 넘기며 창 제목이 메모가 될 때 Ctrl+W를 보내려 했다. 첫 Ctrl+Tab에 되살린 탭으로 넘어가자 메모장 안에 "지정된 경로를 찾을 수 없습니다" 알림이 떴고(그 탭의 파일이 그 자리에 없음), 그 뒤로는 키가 먹지 않아 25번 눌러도 탭이 그대로였다. 아무 탭도 닫거나 바꾸지 않았다 (지나간 탭은 모두 "수정되지 않음" 그대로). 알림을 "확인"으로 닫자 메모장이 파일이 없는 탭 2개(수정되지 않은 것)를 목록에서 뺐다 — 저장 안 한 글이 있던 탭 2개는 그대로 남았다.
    - **지금 방법(UI 자동화)**: 메모장 탭은 UI 자동화(화면 읽기 프로그램이 쓰는 윈도우 기능)로 `"파일이름. 수정되지 않았습니다."` 같은 이름의 탭 항목으로 보인다. 이름이 정확히 그 파일인 탭을 골라(Select) 그 탭에 달린 "탭 닫기" 단추를 누른다(Invoke). 키를 쓰지 않아 다른 탭에 글자가 들어갈 일이 없다. 시험용 파일로: 뒤에 있던 탭 닫기 0.8초, 다른 탭 그대로. 한 번 더 부르면 "찾지 못함"(아무것도 안 닫음).
    - **저장 안 한 탭은 닫기 단추 대신 점(●)이 있어 단추가 없다** → 그때만 Ctrl+W(보이는 탭만 닫는 단축키). 보내기 바로 앞에 키보드 초점이 그 메모장 창 안인지, 창 제목이 그 파일인지(`*파일 - 메모장`), 확인 창이 없는지 다시 본다.
    - **메모장의 저장 여부 창은 별도 창이 아니라 창 안의 팝업**("변경 내용을 …에 저장하시겠습니까?" 저장 / 저장하지 않음 / 취소)이라 `list`의 `waiting`(창 사용 안 함)으로는 안 보인다. 팝업 창 안의 `PrimaryButton`·`SecondaryButton`·`CloseButton`으로 찾는다 (탭에 마우스를 올리면 뜨는 설명 팝업도 같은 "Popup"이라 단추로 구분). 시험: 수정한 시험 탭 → 0.8초 만에 "답 기다림", "저장하지 않음"을 누르자 탭만 닫힘, 파일 내용 그대로.
    - UI 자동화는 PowerShell(`-EncodedCommand`)로 부른다. 이 PC는 PowerShell 스크립트 파일 실행이 막혀 있지만(실행 정책) 명령으로 넘기는 방식은 정책과 상관없이 동작했다 (정책은 바꾸지 않음). 한 번에 0.5~0.8초.
    - 체험판에서 (`SIDEBAR_DEBUG`): 선생님 탭 2개가 있는 메모장에 진행 메모가 탭으로 열림(3.7초) → ✕ → 창 안 닫힘·안내와 단추 → 단추 → "탭을 닫았습니다 (메모장의 다른 탭은 그대로)", `findtab`으로 메모 탭 0개·선생님 탭 그대로 확인.
    - 사이드바가 메모장을 새로 켠 창의 ✕는 단위 테스트로만 확인했다 (시험 중 열린 메모장 창에 선생님의 저장 안 한 탭이 있어 그 창을 닫지 않았다). 선생님 확인 항목에 넣었다.
    - 저장 여부에 답하기를 기다리는 동안은 1.5초마다 창 제목만 읽고(최대 약 1분 반), 보이는 탭이 바뀌면 한 번만 UI 자동화로 탭이 남았는지 본다. 계속 도는 감시는 아니다.

## 윈도우 설치판 (2026-11-22, 브랜치 `win/installer`)
맥 설치판(#13)과 같은 electron-builder 26으로 만든다. 만드는 법은 `app/README.md` "설치판 (윈도우)". 시험은 이 노트북 + 외부 모니터 MB16NCG(200%), 선생님의 개발용 사이드바(`npm start`, 접힌 상태)가 켜져 있는 채로 했다.
1. **만드는 것** (`npm run dist:win`, 이 PC에서 약 3분): `lesson-sidebar-0.1.0-win-setup.exe`(설치 파일, NSIS, 122MB)와 `lesson-sidebar-0.1.0-win-portable.exe`(설치 없이 켜는 파일, 111MB). 둘 다 64비트(x64)만. 앱 폴더는 358MB (대부분 Electron).
   - 설치 파일은 **한 번 누르면 끝나는 방식**(`nsis.oneClick`) + **사용자 폴더 설치**(`perMachine: false`): 묻는 것 없이 `%LOCALAPPDATA%\Programs\lesson-sidebar`에 설치하고 바로 켠다. **관리자 권한 창이 뜨지 않는다.**
   - 실행 파일 이름은 맥처럼 영어 `LessonSidebar.exe`(`build.productName`), 바로 가기·제거 목록 이름은 "수업 사이드바"(`nsis.shortcutName`·`uninstallDisplayName`). 설치 프로그램의 물음 창은 안쪽 이름을 써서 "LessonSidebar을(를) 제거 하시겠습니까?"처럼 나온다.
   - 맥 전용 `extraResources`(맥 도우미 `winctl`, `ko.lproj`·`en.lproj`)는 `build.mac.extraResources`로 옮겼다 (윈도우 빌드에서 맥 도우미 파일을 찾다 멈추지 않게. 맥 결과물은 같아야 함 — 맥 자동 검사로 확인).
2. **도우미 넣기**: `poc/win-helper/winctl.js`·`package.json`(`"type": "module"`)과 `node_modules/koffi`·`node_modules/@koromix/koffi-win32-x64`(koffi 3은 운영체제별 바이너리가 따로 있는 꾸러미)를 `resources/win-helper`에 (3MB). electron-builder는 복사 원본의 맨 위 `node_modules` 폴더를 빼 버려서, `node_modules`를 따로 원본으로 잡아 복사한다. 앱은 원래대로 `process.resourcesPath\win-helper\winctl.js`를 자기 실행 파일 + `ELECTRON_RUN_AS_NODE=1`로 돌린다 (`main.js`의 `makeHelper()`는 고칠 것 없었음). Electron fuses는 설정하지 않아 `RunAsNode`가 켜진 그대로다.
3. **npm "allow-scripts" 경고**: npm 11.17이 설치 스크립트 두 개를 막았다 — `electron-winstaller`(Squirrel 설치 방식용, 이 설치판은 NSIS라 안 씀), `koffi`(미리 만든 바이너리를 고르는 스크립트인데 `@koromix/koffi-win32-x64`에 이미 들어 있어 없어도 동작). **둘 다 허용하지 않았다** (`npm approve-scripts` 안 함). Electron 내려받기는 원래대로 `npm run electron:get`이 한다.
4. **켜 보기 검사** (`npm run smoke:win`, `app/scripts/smoke-packaged.mjs`를 맥·윈도우 같이 쓰게 고침): ① 앱 실행 파일로 도우미 `displays` → 모니터 2개 ② 앱을 켜서 예시 수업 자료 7개 ③ 앱이 도우미로 화면을 읽음(교사 내장 화면, 학생 MB16NCG) ④ 수업 준비 화면 열림 → 통과. 앱 폴더, 설치한 앱, 설치 없이 켜는 파일 모두 통과.
5. **실제 설치** (설치 파일을 더블클릭한 것과 같게 실행): 12.5초 만에 끝나고 사이드바가 저절로 켜짐(0,0 280×1032, 교사 화면 왼쪽). 바탕 화면·시작 메뉴에 "수업 사이드바" 바로 가기, 제거 목록(현재 사용자)에 "수업 사이드바 0.1.0". **이 PC에서 만든 파일이라 SmartScreen 경고는 뜨지 않았다** (인터넷·메신저로 받은 파일에만 붙는 표시가 없음). 다른 PC로 옮긴 파일의 경고 화면은 확인하지 못했다.
   - 바로 가기를 한 번 더 눌러도 사이드바 창은 하나 (두 번째 실행은 바로 꺼짐).
   - 사이드바 창에 정상 닫기 요청(`WM_CLOSE`)을 보내면 프로그램이 끝까지 꺼짐.
6. **설치한 앱으로 수업 동작** (`SIDEBAR_DEBUG=1`로 켜서): 켜지기 1.0초. 자료 A(크롬) 학생 화면에 열기 4.0초, 발표 자료(파워포인트) 5.5초, ⇄ 교사 화면으로·다시 학생 화면으로, 닫기 둘 다 바로 → 통과. 원래 열려 있던 크롬·한글·메모장 창은 그대로.
   - **앞으로 가져오기는 이 시험에서 확인하지 못했다**: 내장 화면에 "연결 프로그램 선택" 창이 맨 앞에 떠 있어서 설치판·개발용 도우미 모두 어떤 창도 앞으로 가져오지 못했다 (위 "알게 된 것" 15). 도우미 코드는 개발용과 같은 파일이라 그 창이 없으면 개발용처럼(약 0.18초) 될 것으로 보지만, 선생님 확인 항목에 넣었다.
   - **그때 찾은 문제 (공통 코드, 개발용도 같음, 이 브랜치에서는 고치지 않음)**: 열린 자료를 다시 눌렀을 때 맨 앞으로 못 가져오면 사이드바가 "창이 닫혀 있어 다시 엽니다"로 **같은 자료를 한 번 더 열었다** (6.4초). 처음 창은 사이드바와 연결이 끊긴 채 학생 화면에 남았다 (시험 뒤 Claude가 정상 닫기 요청으로 닫음). 원인: 윈도우 도우미 `raise`는 창이 있어도 맨 앞이 안 되면 `{"ok":false, front, detail}`로 답하는데, `Helper.call`이 `ok:false`를 오류로 바꾸고 `Session.raiseWid`가 모든 오류를 `'gone'`(창 없음)으로 본다 (`app/src/core/session.js`). 고칠 방향: 오류일 때 `list`로 그 창이 아직 있는지 보고 있으면 `'notfront'`. 다른 PC·학교 PC에서 "앞으로 가져오기"가 막히면 수업 중에도 같은 일이 생길 수 있다.
7. **설치 없이 켜는 파일**: 더블클릭하면 임시 폴더에 풀고 켠다. 켜 보기 검사 전체가 약 10초(설치한 앱은 약 1.6초) → 켜질 때 8~9초 더 걸린다. 설정은 설치판과 같은 `%APPDATA%\수업 사이드바\`.
8. **지우기** (설정 → 앱에서 제거를 누른 것과 같게 `Uninstall LessonSidebar.exe /currentuser`): "LessonSidebar을(를) 제거 하시겠습니까?" → 확인 → 2초 안에 설치 폴더·바로 가기 2개·제거 목록 항목이 모두 없어짐. 설정 폴더 `%APPDATA%\수업 사이드바\`는 남김(다시 설치하면 이어짐).
9. **켜 둔 채 새로 설치할 때** (설치 프로그램 템플릿을 읽어 확인, 직접 해 보지는 않음): "LessonSidebar이(가) 실행 중입니다. OK을 클릭하면 종료됩니다." → OK면 끄기 요청 → 1초 뒤에도 남아 있으면 강제 종료. 사이드바는 끝날 때 "창 비키기"로 옮긴 창을 돌려놓는 데 최대 5초를 쓰므로 그 전에 강제로 꺼질 수 있다 → 안내문에 "끝내기로 끈 뒤 설치"를 적었다.
10. **자동 검사** (`.github/workflows/ci.yml` "윈도우 설치판 만들어 켜 보기"): 설치 파일·설치 없이 켜는 파일 만들기 → 앱 폴더 켜 보기 검사 → 설치 파일을 조용히(`/S`) 설치 → 설치한 앱 켜 보기 검사 → 조용히 지우기. 같은 순서를 이 PC에서 먼저 돌려 통과 (조용히 설치하면 앱이 저절로 켜지지 않아 검사와 겹치지 않음).
