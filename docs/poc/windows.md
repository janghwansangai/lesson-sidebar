## 알게 된 것

1. **앞으로 가져오기**: 명령줄 도우미가 보통 방법(`SetForegroundWindow`)으로 바로 창을 앞으로 가져왔다.
   - 아무도 키보드·마우스를 만지지 않을 때: 0.05초 (실행기 P2)
   - **선생님이 메모장에 글자를 치는 도중** (`raise-lock.js`, 맨 앞: 메모장): 0.06초, 보통 방법으로 성공. 윈도우의 포커스 가로채기 방지가 이 경우에도 막지 않았다. 이 PC의 포커스 잠금 시간(`ForegroundLockTimeout`)은 기본값 200초
   - 다른 PC·학교 PC에서는 막힐 수 있어서, 도우미는 막히면 ① 빈 마우스 입력을 보낸 뒤 다시 시도(PowerToys와 같은 방법) ② `AttachThreadInput` 순서로 자동으로 이어서 시도하고, 어느 방법이 통했는지 `detail.method`에 남긴다. 실제 앱에서는 선생님이 사이드바를 클릭한 직후 사이드바(맨 앞 프로그램)가 부르므로 더 유리하다.
2. **창 제목 형식** (맥과 다름):
   - 파워포인트·엑셀: 확장자까지 붙은 파일 이름 + 프로그램 이름 ("샘플_발표자료.pptx - PowerPoint"). 맥은 확장자 없음. 파일 이름이 들어 있는지로 짝지으므로(`findByTitle`) 둘 다 맞았다.
   - 한글 빈 문서: "빈 문서 1 - 한글"
   - 한글 파일: **"파일이름.hwp [폴더 전체 경로\] - 한글"** — 폴더 경로가 제목에 들어간다. 경로에 윈도우 사용자 이름이 들어갈 수 있으므로 한글 창 제목은 기록·공유하지 않는다. 같은 이름의 파일이 다른 폴더에 있어도 경로로 구분할 수 있다
   - 한글이 이미 다른 문서를 열고 있으면 같은 한글 프로그램 안에 **새 창**(다른 창 번호)으로 연다. 실행기는 자기가 연 창만 닫았고 선생님 문서 창은 그대로 남았다
   - 크롬 "… - Chrome", 웨일 "… - Whale", 엣지 "… - (프로필 이름) - Microsoft Edge"
   - **엣지 제목의 "Microsoft"와 "Edge" 사이에 보이지 않는 글자(폭 없는 공백, U+200B)가 들어 있다.** 창 제목으로 프로그램을 구분하면 안 되고, 실행 파일 이름(`msedge.exe`)으로 구분한다.
3. **브라우저는 창을 닫아도 뒤에서 계속 실행된다** (크롬·엣지). 그래서 실행기의 로컬 파일 제공(127.0.0.1)이 브라우저 연결을 기다리며 끝나지 않았다 → 끝낼 때 연결까지 끊도록 실행기를 고쳤다 (`closeAllConnections`). 실제 앱도 수업을 끝낼 때 같은 처리가 필요하다.
4. **꺼져 있던 브라우저를 `--new-window`로 켜면**: 크롬·웨일은 요청한 창 하나만 열렸다. 엣지는 첫 창에 탭이 하나 더 붙었다 (제목 "수업 사이드바 시험 A 외 페이지 1개"). 엣지의 시작 페이지로 보인다. 이전 창들이 한꺼번에 복원되지는 않았다.
5. **프로그램 열기**: 윈도우는 `cmd`의 `start`(ShellExecute)로 연다. 브라우저는 App Paths에 등록된 이름(`chrome.exe`, `msedge.exe`, `whale.exe`)으로 찾고, 한글은 App Paths에 없어 `.hwp` 파일 연결(`assoc`/`ftype`)에서 실행 파일을 찾았다. 이렇게 연 브라우저는 실행기가 끝나도 계속 살아 있다 (실행기와 떨어진 독립 프로그램).
6. **좌표**: 도우미를 Per-Monitor DPI Aware V2로 설정해 물리 픽셀로 주고받는다. 윈도우 10·11 창에는 보이지 않는 그림자 테두리(약 7픽셀)가 있어서, `SetWindowPos`에 그대로 넣으면 창이 7픽셀 안쪽으로 들어간다. 도우미가 그림자 폭만큼 보정해 보이는 테두리가 요청 위치에 오게 했다 (배치 결과 오차 0).
7. **최소 폭**: 크롬 최소 폭은 배율 100%에서 약 500픽셀, 배율 200% 화면에서 1004 물리 픽셀. 즉 배율을 반영한 약 500이 기준이다 (맥 500포인트와 같다). 분할 계산은 물리 픽셀로 하되, 최소 폭은 배율을 곱해 생각해야 한다.
8. **배율이 다른 화면으로 창을 옮기면 한 번에 안 맞는다.** 창이 새 배율에 맞춰 스스로 크기를 바꾸기 때문이다 (`WM_DPICHANGED`). 도우미가 옮긴 뒤 다시 읽어 어긋나면 한 번 더 맞춘다. 실제 앱도 이 방식을 그대로 쓴다.
10. **외부 모니터를 뺐다 다시 꽂기** (`node runner/replug.js`, 선생님과 함께, 2026-11-21). 학생 화면 왼쪽 반에 크롬 창을 놓고 시험했다.
    - 뺄 때: 도우미가 모니터가 빠진 것을 바로 알아챘고, 윈도우가 창을 노트북 화면 왼쪽 위(0,0)로 옮겼다. 배율이 200% → 100%로 바뀌어 크기도 절반(637×751)이 됐다. 0.6초 안에 자리 잡음. 창은 최소화되지 않고 살아 있었다.
    - 다시 꽂을 때: **윈도우가 창을 학생 화면의 원래 자리 근처로 스스로 되돌려 놓았다** (-2549,0 1280×1493, 원래 -2560,0 1280×1504에서 11픽셀 어긋남). 정확하지 않으므로 사이드바가 다시 놓아야 한다.
    - **다시 꽂은 직후 몇 초 동안은 학생 화면의 작업 표시줄이 아직 없어서, 사용 영역이 화면 전체(높이 1600)로 읽혔다.** 그때 다시 놓은 창은 높이 1600이 되어 나중에 생긴 작업 표시줄(96)에 가려진다. 조금 뒤 다시 읽으니 1504로 돌아왔다. → 실제 앱은 모니터가 다시 연결되면 바로 한 번 놓고, 사용 영역이 바뀌는 신호(Electron `display-metrics-changed`의 `workArea`)가 오면 한 번 더 놓아야 한다.
11. **꺼졌다 켜진 브라우저는 마지막으로 창을 닫은 화면에 새 창을 연다.** 앞 시험에서 학생 화면에 있던 크롬 창을 닫았더니, 다음 새 창이 학생 화면에 열렸다. 수업 중에는 준비되지 않은 창이 학생에게 잠깐 보일 수 있다. 사이드바가 새 창을 찾는 즉시(1.4초 안) 정해진 화면으로 옮기면 되지만, 계획서의 "모두 미리 열기"를 수업 전에 하는 편이 안전하다.
